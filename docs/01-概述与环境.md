## 一、MCP 是什么？（用大白话讲）

### 1.1 一个生活中的类比

想象你搬进一间新房子，墙上有一堆电器要插电。

**没有统一标准的世界：**

- 台灯要用 A 型插孔
- 电脑要用 B 型插孔
- 手机充电器要用 C 型插孔
- 每买一个新电器，就得在墙上凿一个新样子的洞

**有统一标准的世界（就是现在的插座）：**

- 墙上都是标准插座
- 任何电器，插上就能用
- 电器厂商不用管你家墙长什么样，你也不用管电器原来设计给谁用

**MCP 就是 AI 工具世界的那个「标准插座」。**

**MCP = Model Context Protocol = 模型上下文协议**

拆开看：

- **Model（模型）**：Claude、GPT 这些大模型
- **Context（上下文）**：模型能看到的信息，这里特指「工具」
- **Protocol（协议）**：一套双方都遵守的约定

一句话：**MCP 是一套让 AI 能标准化地「发现工具、调用工具」的协议。**

### 1.2 MCP 的完整流程（类比版）

```
你问 AI："北京今天天气怎么样？"
        ↓
    ① 握手（Initialize）
        → 就像你打开工具箱前，先确认"这个箱子里有什么工具"
        ↓
    ② 发现工具（tools/list）
        → 就像你翻开工具清单："有锤子、螺丝刀、卷尺..."
        ↓
    ③ 模型决策（LLM 决定调哪个）
        → 就像你看了一眼清单，心想"这个活儿得用卷尺"
        ↓
    ④ 调用工具（tools/call）
        → 就像你拿起卷尺去量
        ↓
    ⑤ 拿到结果，继续推理
        → 就像你量到了 3 米，然后基于这个数字继续干活
        ↓
    输出："北京今天多云，11°C，建议穿外套。"
```

**注意 ③ 和 ④ 是两件事。** 这是理解 MCP 最关键的分界线，下一节详细讲。

## 二、为什么需要 MCP？

### 2.1 没有 MCP 的世界：N × M 问题

假设你有 **3 个模型** 和 **5 个工具**：

```
        工具1   工具2   工具3   工具4   工具5
Claude   ✍️     ✍️      ✍️      ✍️      ✍️
GPT      ✍️     ✍️      ✍️      ✍️      ✍️
本地模型  ✍️     ✍️      ✍️      ✍️      ✍️
```

**15 份胶水代码。** 而且：

- 加一个新工具，要改 3 个地方
- 换个新模型，要写 5 份适配

**有 MCP 之后：**

```
        工具1   工具2   工具3   工具4   工具5
Client   ─────────── MCP 协议 ───────────
```

工具方实现一次 **MCP Server**，模型方实现一次 **MCP Client**，中间用统一协议对话。

**3 + 5 = 8 份**，而且新增工具只影响工具侧，完全不用动客户端。

### 2.2 一张图理解 MCP 的价值

```
┌─────────────────────────────────────────────────────────────┐
│                      你的 AI 应用                            │
└─────────────────────────────────────────────────────────────┘
                              ↓
                    ┌───────────────────┐
                    │   MCP Client      │  ← 只实现一次
                    │  （与协议对话）    │
                    └───────────────────┘
                              ↓
        ┌─────────────────────┼─────────────────────┐
        ↓                     ↓                     ↓
┌───────────────┐   ┌───────────────┐   ┌───────────────┐
│  MCP Server   │   │  MCP Server   │   │  MCP Server   │
│   文件系统     │   │   数据库      │   │  内部 API     │
├───────────────┤   ├───────────────┤   ├───────────────┤
│ Python 写的   │   │ Java 写的     │   │ Node 写的     │
│               │   │               │   │               │
│ ✅ 客户端完全 │   │ ✅ 不用关心   │   │ ✅ 语言无关   │
│    不关心     │   │    语言       │   │               │
└───────────────┘   └───────────────┘   └───────────────┘
```

**语言无关是这个协议最值钱的地方。**

你的 MCP Client 是 Java 写的，照样能调一个 Python 写的 MCP Server——
因为它俩只通过「启动命令 + stdio 上的 JSON-RPC」对话。

### 2.3 ★ MCP 和 Function Calling 到底什么关系？

**这是面试最爱问、也最容易答错的问题。**

先说结论：**它们不是竞品，是两层，互相正交。**

```
┌─────────────────────────────────────────────────────────┐
│  Function Calling（模型侧）                              │
│  「模型怎么表达：我想调用某个工具」                        │
│  例：Claude 返回 stop_reason="tool_use" + 一个 tool_use 块│
└─────────────────────────────────────────────────────────┘
                          ↕  正交
┌─────────────────────────────────────────────────────────┐
│  MCP（工具侧）                                           │
│  「工具怎么被发现、怎么被调用」                            │
│  例：tools/list 列出有哪些工具，tools/call 执行           │
└─────────────────────────────────────────────────────────┘
```

**三个能帮你记牢的事实：**

| 事实 | 说明 |
|---|---|
| MCP Server **可以完全不用 LLM** | 任何普通程序都能调它。本教程 Demo 1 就故意这么写 |
| Function calling **可以调非 MCP 的工具** | 你手写 30 行 JSON Schema 就是，根本不涉及 MCP |
| 两者**需要一层薄胶水**才能连起来 | 把 MCP 工具转成 Claude 工具格式，Demo 2 会写，只有 30 行 |

**为什么容易混？** 因为两者经常一起出现，而且都用 JSON Schema。

**一个精准的判断方法：**

> 如果你在写「模型的提示词、工具定义、解析 tool_use」——那是 function calling。
> 如果你在写「启动一个子进程、收发 JSON-RPC、列工具清单」——那是 MCP。

## 三、技术选型说明

### 3.1 为什么选这些技术？


| 技术 | 选型 | 为什么选它 | 类比理解 |
| --- | --- | --- | --- |
| MCP SDK | `io.modelcontextprotocol.sdk:mcp` 2.0.0 | 官方维护，目前稳定版 | MCP 协议的「官方翻译官」 |
| 传输方式 | STDIO | 本地子进程，零网络配置 | 两个人面对面说话 |
| LLM SDK | `com.anthropic:anthropic-java` 2.34.0 | 官方 Java SDK | 给 Claude 打电话的座机 |
| 数据库 | H2 内存库 | 纯 Java，零安装 | 练习用的草稿纸 |
| 日志 | slf4j-simple | 默认走 stderr | 见下面的「头号杀手」 |

### 3.2 关键概念速查表


| 概念 | 一句话解释 | 类比 |
| --- | --- | --- |
| **MCP** | 工具与模型之间的标准协议 | 墙上的标准插座 |
| **Host** | 用户面对的那个应用 | 你的房子 |
| **Client** | Host 内部与**单个** Server 的连接器 | 一个插头 |
| **Server** | 提供工具的一方 | 一个电器 |
| **Transport** | 两者怎么通信 | 电线 |
| **STDIO** | 用标准输入输出通信（本地子进程） | 面对面说话 |
| **Streamable HTTP** | 用 HTTP 通信（远程服务） | 打电话 |
| **tools/list** | 发现有哪些工具 | 看工具清单 |
| **tools/call** | 调用某个工具 | 拿起工具干活 |
| **JSON-RPC 2.0** | 消息的格式，MCP 直接复用它 | 双方约定的语法 |
| **capability** | 双方各自声明支持什么 | 交换名片 |

**⚠️ 一个必须记住的比例关系：Client 和 Server 是 1:1。**

一个 Host 可以持有多个 Client，每个 Client 连一个 Server。

```
Host
 ├── Client A ── Server A（文件系统）
 ├── Client B ── Server B（数据库）
 └── Client C ── Server C（自研）
```

**不是**一个 Client 连三个 Server。这是新手最常画错的架构图。

### 4.2 依赖配置

完整 `pom.xml` 见 [`02-Demo1-最小MCP链路.md`](./02-Demo1-最小MCP链路.md) 第 3.1 节。核心就三块：

```xml
<properties>
  <maven.compiler.release>17</maven.compiler.release>
  <mcp.sdk.version>2.0.0</mcp.sdk.version>
  <anthropic.sdk.version>2.34.0</anthropic.sdk.version>
</properties>

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>io.modelcontextprotocol.sdk</groupId>
      <artifactId>mcp-bom</artifactId>
      <version>${mcp.sdk.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>
    <groupId>io.modelcontextprotocol.sdk</groupId>
    <artifactId>mcp</artifactId>
  </dependency>
  <dependency>
    <groupId>com.anthropic</groupId>
    <artifactId>anthropic-java</artifactId>
    <version>${anthropic.sdk.version}</version>
  </dependency>
</dependencies>
```

**关于 `mcp` 这个构件**：它是个便捷包，等于 `mcp-core` + Jackson3 JSON 实现 + 传输实现。
想更精细控制依赖，可以只引 `mcp-core` 并自己挑 JSON 实现。

### 4.3 三个必须配对的构建细节

这三个如果不配，后面一定会踩坑。**坑的详细解释见第七节。**

**① 用 `exec:exec` 而不是 `exec:java`**

```xml
<plugin>
  <groupId>org.codehaus.mojo</groupId>
  <artifactId>exec-maven-plugin</artifactId>
  <version>3.5.0</version>
  <configuration>
    <executable>java</executable>
    <arguments>
      <argument>-Dfile.encoding=UTF-8</argument>
      <argument>-Dstdout.encoding=UTF-8</argument>
      <argument>-Dstderr.encoding=UTF-8</argument>
      <argument>-classpath</argument>
      <classpath/>
      <argument>${mainClass}</argument>
      <argument>${appArgs}</argument>
    </arguments>
  </configuration>
</plugin>
```

**② 三个编码参数一个都不能少**

Windows 中文环境特有：Java 18+ 的 `file.encoding` 已经是 UTF-8 了，
但 `System.out` 走的是 `stdout.encoding`，它**仍然跟随控制台代码页**（中文系统是 GBK）。

结果：文件读写正常，`println` 出来的中文全是乱码。

**③ 日志必须走 stderr**

STDIO 传输把 **stdout 独占为 JSON-RPC 通道**。
任何打到 stdout 的东西——`System.out.println`、日志框架的默认输出、
某个依赖库的调试信息——都会污染协议流。

## 七、五个必踩的坑（先看，能省几小时）

按踩到概率排序，前三个几乎人人中招。

### ① stdout 被污染（头号杀手）

**症状**：客户端报 JSON 解析错误；或者干脆卡住不动；或者 `initialize` 就失败。

**原因**：STDIO 传输把 stdout 当成独占的 JSON-RPC 通道。

**常见污染源**：

- `System.out.println("debug")` ← 最常见
- 日志框架默认输出到 stdout（Logback 默认就是）
- 某个依赖库自己 print 东西

**解法**：日志统一走 stderr，调试信息用 `System.err`。

### ② Windows 中文乱码

**症状**：文件读写正常，但 `System.out.println` 出来的中文全是 `?????`。

**原因**：Java 18+ 的 `file.encoding` 是 UTF-8，但 `System.out` 走 `stdout.encoding`，
它在 Windows 上跟随控制台代码页（GBK）。

**解法**：三个参数缺一不可。

```
-Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8
```

注意：**fork 子进程时也要带上**，否则子进程的日志照样乱码。

### ③ 孤儿进程

**症状**：程序跑完，任务管理器里一堆 `java` 进程不走。

**原因**：官方 SDK 的 stdio server **在 stdin 关闭后不会自己退出**。
官方示例通常写成 `new CountDownLatch(1).await()`（永久阻塞），
客户端崩了 server 就变孤儿。

**解法**：server 端自己感知 stdin EOF（见 `core/StdioLifecycle.java`）。

### ④ `-Dexec.args` 不能用

**症状**：参数被当成主类名，报 `ClassNotFoundException`。

**原因**：exec 插件把 `exec.args` 插到**主类名之前**。

**解法**：用自定义属性 `-DappArgs=`，在 `<arguments>` 里显式放在主类名后面。

### ⑤ 忘了 `closeGracefully()`

**症状**：同 ③，但原因在客户端。

**解法**：`try/finally` 兜底。

```java
try (McpSyncClient client = ...) {
    // ...
}  // 或者 try/finally 手动调 closeGracefully()
```
