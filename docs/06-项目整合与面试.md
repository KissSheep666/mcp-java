### 1.2 核心流程代码

整个项目的主线，剥掉所有细节，就是这一段：

```java
// ① 起 MCP Client（子进程 + 握手）
McpSyncClient mcp = McpClient.sync(new StdioClientTransport(serverParams, jsonMapper))
        .build();
mcp.initialize();

// ② MCP 工具 → Claude 工具（30 行胶水）
List<Tool> claudeTools = mcp.listTools().tools().stream()
        .map(McpToClaudeTool::toClaudeTool)
        .toList();

// ③ agent loop
List<MessageParam> messages = new ArrayList<>();
messages.add(MessageParam.builder().role(USER).content(question).build());

for (int turn = 1; turn <= MAX_TURNS; turn++) {
    Message response = claude.messages().create(params);   // 发给模型

    for (ContentBlock block : response.content()) {
        if (!block.isToolUse()) continue;

        ToolUseBlock toolUse = block.toolUse().orElseThrow();
        Map<String, Object> args = toolUse._input().convert(Map.class);

        // ④ 模型要调工具 → 通过 MCP 执行
        McpSchema.CallToolResult r = mcp.callTool(
                new McpSchema.CallToolRequest(toolUse.name(), args));

        toolResults.add(...);                              // 包成 tool_result
    }

    if (toolResults.isEmpty()) break;                      // ⑤ 模型不再要工具 → 结束
    messages.add(工具结果);
}
```

**如果面试官只给你 5 分钟，讲这段就够了。**

## 二、简历写法

### 2.1 项目描述

**⚠️ 先说实话：这是一个学习项目，不是生产项目。**

写简历时不要夸大。诚实的写法反而更容易通过面试——
因为面试官一追问细节，夸大的人会立刻露馅。

**推荐写法（诚实版）：**

> **AI 工具接入平台（MCP 协议实现）｜个人项目**
>
> 基于 MCP（Model Context Protocol）Java SDK 实现了一套标准化的 AI 工具接入方案，
> 支持将内部系统（数据库等）以标准协议暴露给大模型调用。
>
> - 实现 MCP Server/Client 全链路，含握手协商、工具发现、工具调用
> - 实现只读数据库查询 MCP，暴露 4 个工具，支持自然语言查库
> - 设计三层安全模型（数据库只读账号 / SQL 白名单 / 查询超时限流），
>   通过 12 个攻击用例与误伤用例验证
> - 实现审计日志，记录全部工具调用（含被拒绝的请求）
> - 通过 JDBC 元数据接口实现表结构自省，将数据库注释转化为模型上下文

**如果你想写得更强，建议先做这两件事：**

1. 接一个真实的数据源（哪怕是你自己的测试库）
2. 加一个连接池和结果缓存（`只读数据库MCP.md` 第 8 节列了清单）

**做了这两件，就可以理直气壮地说「生产级」了。**

## 三、面试话术

### 3.1 项目介绍（1 分钟版）

> 我做过一个基于 MCP 协议的工具接入项目。
>
> 背景是我发现，把内部系统接给 AI 用的时候，每接一个系统都要写一遍适配代码，
> 而且换个模型又得重写。MCP 是 Anthropic 提出的一个标准协议，
> 把这部分标准化了——工具方实现一次 Server，模型方实现一次 Client，中间用统一协议对话。
>
> 我的项目分四步做的：
>
> 第一步先手写了一个最小 MCP 链路，**故意不接 LLM**，
> 这样可以清楚地理解「MCP 是程序调工具的协议，和 function calling 是两层正交的东西」。
>
> 第二步把 Claude 接进来，实现了 agent loop。
> 这一步我发现桥接层只要 30 行，因为 MCP 和 Claude 用的是同一套 JSON Schema。
>
> 第三步做了个真实场景：只读数据库查询。暴露 4 个工具，
> 让 AI 能用自然语言查库。这一步最大的体会是——
> **模型看不见你的库，它的 SQL 写得对不对，九成取决于你怎么描述表结构。**
>
> 第四步是安全加固。我设计了三道墙：
> 数据库只读账号挡攻击、SQL 白名单挡误操作、超时限流防拖垮。
> 其中只读账号是唯一不可替代的一环，因为它不依赖我的代码写得对。
>
> 验证方面我写了 12 个攻击用例和误伤用例，
> 包括用注释拼接关键字绕过这种手法，都拦住了。

### 3.2 技术深挖话术

**被问「MCP 和 function calling 什么关系」时：**

> 它们是**正交的两层**，不是竞品。
>
> Function calling 是模型侧的机制——模型输出一个 `tool_use` 块表示「我想调某个工具」。
> MCP 是工具侧的机制——工具怎么被发现（`tools/list`）、怎么被调用（`tools/call`）。
>
> 两个可以独立存在：
> MCP Server 可以被一个完全没有 LLM 的程序使用——我在 Demo 1 里就是这么验证的；
> 反过来，function calling 也可以调完全不走 MCP 的、手写的工具。
>
> 需要两者配合时，中间要一层胶水。我这层胶水只有 30 行，
> 因为两边用的是同一套 JSON Schema，本质只是把 schema 从左口袋挪到右口袋。

**被问「为什么不直接用 prompt 限制只允许 SELECT」时：**

> 因为 prompt 不是安全边界。三个理由：
>
> 一是模型会犯错——你说「删掉过期记录」，它可能真生成 DELETE。
> 二是模型会被操纵——提示注入可以绕过任何提示词约束。
> 三是安全必须是确定性的，不能依赖一个概率性组件每次都做对。
>
> 正确做法是把边界做在模型管不到的地方。
> 我的项目里是三道墙：数据库只读账号、代码层 SQL 白名单、超时限流。
>
> 其中只读账号最重要，因为它是唯一不依赖「我的代码写得对」的一道。
> 就算 SqlGuard 有绕过路径，DELETE 到数据库也会被拒。

**被问「SQL 校验怎么做的」时：**

> 核心是**掩码 + 分词 + 白名单**。
>
> 掩码是把字符串字面量、引号标识符、注释全部替换成**等长空格**，
> 只留语法给校验器看。
>
> 为什么要掩码？因为像 `WHERE name = 'delete me'` 这种正常查询，
> 里面的 DELETE 是数据不是语法，不掩码会误伤。
>
> 为什么等长？这样掩码串和原串下标一一对应，后面定位修改 LIMIT 时可以直接映射。
>
> 为什么要手写状态机而不是正则？因为要正确处理 `''` 转义引号、
> 注释里包引号、未闭合引号这些情况，正则做不到。
>
> **但我要强调：手写的解析器理论上不可能完备。**
> 所以它的定位是「挡住模型不小心写错的 99%」，真正挡攻击靠只读账号。

**被问「怎么让模型把 SQL 写对」时：**

> 我的排序是：
>
> 第一，**补全数据库表注释**，性价比最高。
> 我通过 JDBC 的 `DatabaseMetaData.getColumns()` 读 `REMARKS` 字段，
> 把 `COMMENT ON COLUMN` 的中文注释喂给模型。
> 模型看不懂 `spare_code`，但看得懂「物料编码，业务唯一键」。
>
> 第二，**写好工具描述**。公式是「做什么 + 什么时候用」。
> 比如 `describe_table` 的描述我写的是
> 「写查询前如果不确定字段名或字段含义，必须先调用这个工具——不要凭猜测写字段名」。
> 正是这句话让模型形成了「先看表、再看结构、最后写 SQL」的习惯。
>
> 第三，**把数据库报错原样回传给模型**。它看到 Table not found 通常能自己改对。

## 五、进阶话题（加分项）

如果面试官问得更深，或者你想继续做下去。

### 5.1 当前实现的局限

**主动说出局限，比被问出来强得多。**

| 局限 | 影响 | 怎么改进 |
| --- | --- | --- |
| 手写 SQL 解析器不完备 | 理论上有绕过路径 | 用 JSqlParser 做真正的 AST 解析 |
| 每次查询新建连接 | 高并发下打爆数据库 | HikariCP 连接池 |
| 无结果缓存 | 相同查询重复执行 | 按 SQL 哈希缓存 30 秒 |
| 无数据脱敏 | 模型可能查出手机号、身份证号 | 结果集过脱敏规则 |
| 无行级权限 | 所有用户看到的数据一样 | SQL 外套 WHERE，或按用户切换账号 |
| 工具结果截断粗暴 | 按 4000 字符硬切 | 只回传摘要 + 让模型按需再查 |

**其中连接池和结果缓存是最该先做的两个。**

### 5.2 值得深入的方向

**① SQL 解析的正确姿势**

手写分词器做的是「词法层面」的检查。真正完备的做法是**语法层面**：

```
手写分词器  →  只能看到 token 序列，判断不了语法结构
JSqlParser  →  生成 AST，可以精确判断"这是一条 SELECT 还是 DELETE"
```

代价是引入依赖、且要适配不同方言。

**② MCP 的工具搜索**

当工具多到几十个时，全部塞给模型会稀释注意力。
Claude 有个「工具搜索」能力：工具标记 `defer_loading: true`，
模型按需搜索加载，而不是一次性全给。

而且它**不破坏 prompt cache**（工具是追加而不是替换）。

**③ Sampling —— Server 反向借 LLM**

MCP 有个容易被忽略的能力：**Server 可以反向请求 Client 帮忙调一次 LLM。**

意味着一个 MCP Server 可以做到「我不内置任何模型，但需要推理时向 Host 借用」。

```java
.toolCall(someTool, (exchange, request) -> {
    var result = exchange.createMessage(/* CreateMessageRequest */);
    ...
})
```

**④ 多 Server 编排**

真实场景往往要接多个 MCP Server（文件系统 + 数据库 + 内部 API）。
这时候要考虑：

- 工具命名冲突怎么解决
- 工具太多怎么筛选（工具搜索 or 网关层过滤）
- 一个 Server 挂了怎么降级

**这就是「MCP 聚合网关」这类东西存在的理由。**

## 六、总结

### 6.1 你学到了什么

```
Demo 1  最小 MCP 链路
        → MCP 是「程序调工具」的协议，和 LLM 无关
        → 握手、能力协商、JSON-RPC

Demo 2  接上 LLM
        → agent 本质就是个 while 循环
        → tool_use / tool_result 的往返
        → 桥接层只有 30 行，因为两边用同一套 JSON Schema

Demo 3  只读数据库 MCP
        → 模型看不见你的库，工具描述和表注释决定它的表现
        → 架构分层的价值：换库只改一个文件

Demo 4  安全与加固
        → 安全必须做在模型管不到的地方
        → 三道墙的定位各不相同，只读账号不可替代
```

### 6.2 三句话记住这个项目

1. **MCP 是工具侧的标准化协议，和模型侧的 function calling 正交。**
2. **agent 就是一个 while 循环，没有更玄的东西。**
3. **安全不能靠 prompt，必须做在模型管不到的地方。**

### 6.3 下一步

如果你想继续深入，按这个顺序：

1. **接一个真实的数据源**（测试库，不是生产库）
2. **加连接池和结果缓存** —— 最接近生产的两个改进
3. **用 JSqlParser 替换手写解析器** —— 把安全层做扎实
4. **试试 Streamable HTTP** —— 把 Server 部署成远程服务
5. **接多个 MCP Server** —— 体验真实的工具编排问题
